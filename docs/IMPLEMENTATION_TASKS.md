# Поэтапные задачи реализации

Архитектура: Python индексирует архив на ПК; Kotlin обеспечивает Android-интерфейс и исполнение E5-small; Rust владеет локальным индексом и выполняет гибридный поиск. Обновления доставляют готовые снимки. Подробности моделей и данных — в [DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md).

Чек-листы описывают полный объём задач; фактический статус — в [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md). Основные команды сборки уже реализованы и описаны в `README.md`. ПК: 16 ГБ RAM, 8 ГБ VRAM. Первая мобильная цель — подключённое устройство arm64, Android 14 / API 34; минимальная версия приложения — API 26.

## Этап A. Проверить техническую основу

### T01. Создать структуру и воспроизводимую сборку

- [ ] Создать Cargo workspace: `search-core`, `search-jni`, `search-cli`; Python-проект `indexer/`; Android-проект Kotlin/Compose.
- [ ] Зафиксировать Rust toolchain, Python, JDK, Gradle, Android SDK/NDK и минимальную версию Android. Выбирать совместимые версии по документации используемых runtime.
- [ ] Настроить сборку `.so` для `arm64-v8a`; `x86_64` добавить для эмуляторных проверок.
- [ ] Задокументировать локальные настройки и исключить сессии, модели, архивы, базы и ключи из Git.

**Зависимости:** нет. **Готовность:** Rust CLI запускается на ПК; Android debug APK загружает Rust-библиотеку и получает её версию. Целевые проверки: `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, `./gradlew assembleDebug` из `android/`.

### T02. Проверить E5-small на ПК и Android

- [ ] Зафиксировать revision `intfloat/multilingual-e5-small`, токенизатор, префиксы, masked mean pooling, L2-нормализацию и максимальную длину.
- [ ] Подготовить экспорт и INT8-кандидат; выбрать Android runtime по успешному запуску, не переносить inference в Rust без необходимости.
- [ ] Проверить кириллицу, emoji, пустой ввод, длинные запросы и усечение.
- [ ] Сравнить исходную модель, экспорт на ПК и тот же экспорт на телефоне: векторы и top-k на фиксированном наборе.
- [ ] Замерить холодный/тёплый запуск, p50/p95 задержки и пиковую RAM; определить приемлемые пределы на целевом телефоне.

**Зависимости:** T01. **Готовность:** в `docs/benchmarks/` есть отчёт, зафиксированы артефакт модели и допустимые отклонения. Если качество или память неудовлетворительны, модель меняем до массовой индексации.

### T03. Проверить генерацию описаний на ПК

- [ ] Проверить доступность и пригодность ядра `DAEMON_NAMES_MEMES`; его переиспользование не должно блокировать независимый прототип.
- [x] Внедрить основной быстрый backend Florence-2-base-ft + отдельный OCR ru/en, фиксированные артефакты, локальный GPU и кеш профиля.
- [ ] Оценить качество и скорость Florence на репрезентативных 100–500 изображениях; отдельно проверить Qwen3-VL-4B-Instruct для сложных мемов.
- [ ] Сохранять структурированные поля: сцена, OCR, предполагаемый смысл, версии обработки. Не выдавать интерпретацию за наблюдаемый факт.
- [ ] Измерить VRAM/RAM и время; подобрать число визуальных токенов и длину ответа. Сохранять результаты после каждой картинки.

**Зависимости:** T01. **Готовность:** проход завершён в пределах доступной памяти; выявлены ошибки OCR и выдуманные детали. Есть конфигурация запуска и возможность продолжить обработку.

**Условие перехода:** T02 и T03 подтверждают, что выбранный стек работает на имеющемся оборудовании.

## Этап B. Контракт и Rust-ядро

### T04. Определить снимок v1 и API ядра

- [ ] Описать JSON-манифест, SQLite-схему, Float32 little-endian векторы размерности 384 и связь строк с видами описаний.
- [ ] Определить отдельно ключи сообщений, медиа и контекстных представлений; учесть несколько источников одного изображения.
- [ ] Зафиксировать даты UTC, nullable отправителя, username как атрибут, темы, ссылки и группы дублей.
- [ ] Зафиксировать API сессии: `open`, `validate`, `search`, `cancel`, `close`; ошибки, ограничения top-k и формат фильтров.
- [ ] Создать маленький искусственный пакет и ожидаемые результаты, без приватных данных.

**Зависимости:** T02. **Готовность:** спецификация в `contracts/` однозначно описывает чтение пакета Python и Rust; необязательная интерпретация не требует фиктивного вектора.

### T05. Реализовать чтение и проверку в Rust

- [ ] Проверять версии, embedding space, хеши, размеры файлов, число и конечность чисел в векторах, ссылки между таблицами и строками.
- [ ] Открывать SQLite только для чтения; выбрать и зафиксировать сборку с FTS5 на ПК и Android.
- [ ] Владеть данными внутри ядра. Если используется mmap, отображать только неизменяемые файлы с корректным временем жизни.
- [ ] Добавить `search-cli validate <snapshot-dir>`.

**Зависимости:** T04. **Готовность:** валидный пакет открывается, несовместимые и повреждённые данные возвращают понятные ошибки без аварийного завершения. Проверены одинаковые FTS-возможности ПК/Android.

### T06. Реализовать точный векторный поиск и фильтры

- [ ] Выполнять скалярное произведение нормализованных векторов; отбирать top-k без сортировки всего архива.
- [ ] Ограничивать допустимые сообщения фильтрами по чату, теме, отправителю и датам до отбора кандидатов.
- [ ] Сводить представления к изображениям с подходящими источниками; определить стабильный порядок при равных оценках.
- [ ] Добавить кооперативную отмену и ограничения параллельных запросов.

**Зависимости:** T05. **Готовность:** выдача совпадает с независимым простым эталоном; покрыты несколько представлений, несколько источников, узкие фильтры и отмена. Пока без ANN.

### T07. Реализовать лексический поиск и RRF

- [ ] Индексировать OCR и подписи в FTS5, определить обработку пользовательского ввода и синтаксиса MATCH.
- [ ] Получать лексических кандидатов с теми же фильтрами; объединять ветви RRF по устойчивым идентификаторам.
- [ ] Группировать дубли с сохранением подходящих сообщений. Сделать размеры списков и параметры объединения конфигурируемыми.
- [ ] Добавить диагностический режим CLI для сравнения ветвей. Морфологию и опечатки оценить отдельно.

**Зависимости:** T06. **Готовность:** точная надпись и смысловой запрос находят ожидаемые картинки; отсутствующая ветвь не ломает поиск; дубли не занимают всю выдачу.

### T08. Реализовать JNI и жизненный цикл

- [ ] Передавать одним вызовом текст, вектор, фильтры и top-k, возвращать компактный ответ; индекс остаётся в Rust.
- [ ] Использовать реестр проверяемых handles и явное закрытие. Обработать повторное закрытие, неверный handle, неверную размерность, Unicode и ошибки.
- [ ] Зафиксировать политику panic, не допускать unwinding через JNI. Обычные ошибки возвращать как типизированные результаты.
- [ ] Kotlin вызывает Rust в рабочем потоке; отдельный сигнал отмены доходит до ядра. Закрытие не освобождает ресурсы активного поиска.

**Зависимости:** T07. **Готовность:** инструментальные Android-проверки открытия/поиска/отмены/закрытия проходят, выдача соответствует CLI, циклы открытия не накапливают ресурсы.

## Этап C. Подготовка реального архива

### T09. Реализовать Telegram collector

- [ ] Конфиг: источник, разрешённые чаты, даты и лимиты; авторизация и сессия вне репозитория.
- [ ] Читать историю, скачивать фото и изображения-документы, собирать метаданные и контекст подписи.
- [ ] Обрабатывать FloodWait, сетевые ошибки и недоступные сообщения; сохранять прогресс.
- [ ] Проверять изменения подписи и удаления при явной перепроверке; исключённые чаты не экспортировать.

**Зависимости:** T04. **Готовность:** пилот 1 000–5 000 изображений; остановка и повторный запуск не создают дубли и не теряют прогресс.

### T10. Реализовать проходы обработки и exporter

- [ ] Применить конфигурацию T03; отделить OCR от предположений, создавать превью.
- [ ] После выгрузки VLM генерировать E5-векторы экспортированным артефактом T02. Учитывать изменение модели, промпта и подписи.
- [ ] Сравнить один/два вектора; хранить отсутствующую интерпретацию явно.
- [ ] Экспортировать завершённую SQLite-базу без зависимости от WAL, векторы и манифест с SHA-256 в новую папку версии.
- [ ] Проверять каждый экспорт через Rust CLI до публикации.

**Зависимости:** T03, T05, T09. **Готовность:** реальный пакет валидируется и ищется тем же Rust-ядром, которое используется на телефоне; повторный проход переиспользует неизменившиеся результаты.

## Этап D. Автономный Android MVP

### T11. Реализовать импорт и переключение снимка

- [ ] Kotlin выбирает пакет через системный диалог и копирует его в staging; проверяет свободное место и лимиты распаковки.
- [ ] Запретить пути за пределами staging и опасные ссылки в архиве. Rust проверяет содержимое и открывает новую сессию.
- [ ] Переключать указатель активной версии после полной проверки, сохраняя прежнюю сессию для текущих запросов.
- [ ] Реализовать восстановление после закрытия приложения, уборку staging и откат. Избранное хранить отдельно, если оно включено.

**Зависимости:** T08, T10. **Готовность:** обрыв импорта, нехватка места и битый пакет не портят рабочую базу; поиск во время обновления использует согласованный комплект.

### T12. Реализовать интерфейс поиска

- [ ] Compose: строка поиска, фильтры, список превью, источники дублей и статус снимка.
- [ ] E5 обрабатывает запрос, JNI запускает поиск; новый запрос отменяет старый и устаревшая выдача не попадает на экран.
- [ ] Добавить пустую выдачу, ошибки модели/индекса и открытие сообщений с учётом типа чата и доступа аккаунта.
- [ ] Поиск и локальные превью работают в авиарежиме; Telegram-сессия в поисковике не нужна.

**Зависимости:** T02, T11. **Готовность:** пользователь импортирует пакет, ищет по-русски с фильтрами и открывает исходное сообщение, если его тип и доступ поддерживаются.

### T13. Оценить качество и ресурсы MVP

- [ ] Разметить 30–50 запросов и разделить настройку/проверку; сравнить semantic-only, hybrid и одно/два представления.
- [ ] Измерить Recall@10, nDCG@10, полноту кандидатов и влияние INT8.
- [ ] На 10k/50k/100k картинок измерить p50/p95, RAM, диск, холодный запуск и время импорта. Разделять реальные архивы для качества и искусственные наборы для нагрузки.
- [ ] Утвердить пороги выпуска по измерениям; реранкер оценивать на ПК как отдельный эксперимент.

**Зависимости:** T12. **Готовность:** отчёт объясняет выбранные параметры и ограничения; автономный MVP удовлетворяет зафиксированным порогам.

**Условие перехода:** до автоматических обновлений работает полный сценарий ручного импорта и поиска.

## Этап E. Доставка и выпуск

### T14. Подключить один автоматический транспорт

- [ ] Выбрать HTTPS либо Syncthing. Для HTTPS: неизменяемый пакет, затем latest-манифест, защищённый доступ и продолжение загрузки при поддержке источником.
- [ ] Для Syncthing: актуальный Android-клиент, send-only на ПК, receive-only на телефоне, доступ приложения к папке доставки.
- [ ] В обоих случаях использовать T11; не открывать рабочую базу непосредственно из синхронизируемой папки.
- [ ] Принимать версию только после проверки всех файлов, независимо от порядка их появления. Проверять dataset ID и совместимость модели.

**Зависимости:** T13. **Готовность:** обновление не требует APK; обрыв сети, неполная папка и несовместимая версия сохраняют прежний индекс.

### T15. Подготовить первый выпуск

- [ ] Подписать APK постоянным ключом и подготовить публикацию релизов для Obtainium; ключ не включать в Git.
- [ ] Документировать установку, модель, конфиг collector, сборку снимка, импорт, транспорт и откат.
- [ ] Добавить автоматические проверки Rust, Python, Android-сборки и контракта на искусственных данных.
- [ ] Проверить release APK на физическом устройстве, включая загрузку JNI после оптимизации приложения.

**Зависимости:** T14. **Готовность:** воспроизводимый выпуск, инструкции и полный проверенный сценарий от ПК до телефона. При необходимости внутренний MVP можно выпустить после T13 с ручным импортом.

## Этап F. После MVP

### T16. Оптимизировать по результатам замеров

- [ ] Добавлять SIMD/ANN или квантизацию векторов только при недостаточной скорости/памяти; сохранять точный поиск как эталон.
- [ ] Проверять полноту ANN при узких фильтрах и восстановление индекса на Android.
- [ ] При больших обновлениях добавить неизменяемые части, удаления и периодическую компактизацию.
- [ ] Небольшой мобильный реранкер добавлять только при измеримом улучшении с приемлемой задержкой.

**Зависимости:** T13; для обновлений — T14. **Готовность:** документирован выигрыш и потери качества, сохраняется совместимость или явно повышена версия формата.

### T17. Интегрировать exteraGram

- [ ] Проверить SDK и доступные точки меню на конкретной версии клиента.
- [ ] Python-плагин запускает Kotlin-приложение с фильтром текущего чата; предусмотреть проверку входных параметров и отсутствие приложения.
- [ ] Поиск и обновления остаются в Rust/Kotlin приложении. Не требуется доступ к кешу Telegram.

**Зависимости:** T15. **Готовность:** запуск из чата применяет правильный фильтр, результаты открываются в клиенте; отдельное приложение продолжает работать самостоятельно.

## Очерёдность

Основной путь: **T01 → T02/T03 → T04 → T05–T08 → T09–T10 → T11–T13 → T14–T15**. T03 и T09 допускают работу независимо от отдельных задач ядра после выполнения своих зависимостей. T16–T17 не блокируют первый MVP.

Первое практическое действие: **T01**, затем проверка **T02** на выбранном физическом телефоне. Не индексировать весь архив до успешного экспорта и проверки мобильного энкодера.
